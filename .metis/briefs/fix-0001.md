# fix-0001 — Store reopen straight after close fails intermittently with NotFound

- **Type:** fix | **Risk:** medium | **Priority:** p1
- **Coder:** claude-code/opus-5-5 | **Date:** 2026-11-25
- **Plan:** .metis/plans/phase-0-plan.md §0.3

## Goal

`Store::open` straight after `Store::close` always succeeds, so §0.3's
"a fresh state directory migrates to the current schema and reopens cleanly"
holds every run, not four in five.

## Architectural context

- `crates/ship-store/src/lib.rs` — `Store::close` (pool close), `Store::open_with`.
- `crates/ship-store/src/migrate.rs` — `probe_version` reads the schema
  version read-only: with a non-empty `-wal` it copies `ship.db` and
  `ship.db-wal` to a private temp dir. A `-wal` that SQLite checkpoints and
  unlinks between the size check and `std::fs::copy` surfaces as
  `StoreError::Io(NotFound)` (the reported symptom, tests/store.rs:231).
- A non-empty `-wal` beside a database whose store was just closed means a
  connection was still open when `close()` returned: SQLite removes `-wal`
  and `-shm` when the last connection to a WAL database closes.
  `crates/ship-daemon/tests/sigterm.rs:57` already relies on that.
- `Store::close` keeps its signature (`async fn close(self)`), so the daemon
  is unaffected.

## Declared file scope

- **owned_paths:** crates/ship-store/src/lib.rs, crates/ship-store/src/migrate.rs, crates/ship-store/tests/store.rs, crates/ship-store/Cargo.toml, Cargo.lock
- **read_only_paths:** crates/ship-daemon, crates/ship-core

## Definition of Done

1. `Store::close` returns only once no connection to the database is open,
   shown by `ship.db-wal` and `ship.db-shm` being gone. After the pool closes,
   while either sidecar exists, a barrier connection is opened, reads, and
   closes. The last connection to close checkpoints and removes them. The
   wait is bounded by the busy timeout (5 s).
2. `probe_version` tolerates the `-wal` disappearing between listing and
   reading: a `NotFound` while copying the pair re-checks the WAL. A WAL
   that has gone was fully checkpointed, so the main file is read
   `immutable`. The number of attempts is bounded, and any other error still
   propagates.
3. A regression test loops write → close → open enough times to have caught
   the original 1-in-5 failure, and asserts after every close that no
   sidecar is left.
4. `make verify` (through `metis verify --post`) is green. Twenty
   consecutive runs pass.
5. No new crate enters the dependency graph. `tokio` is already present
   through sqlx's `runtime-tokio`; ship-store takes it directly with the
   `time` feature only.

## Test plan

- `tests/store.rs::close_then_reopen_never_fails`: 200 iterations of open →
  write a project, using several pool connections at once → close → assert
  no `-wal`/`-shm` → the next open succeeds and sees every earlier project.
- `migrate.rs` unit `probe_tolerates_wal_vanishing_mid_copy`: a WAL that is
  removed by the copy step (injected copy function) yields the version from
  the main file instead of `Io(NotFound)`.
- `migrate.rs` unit `probe_propagates_other_copy_errors`: a non-NotFound
  copy error is still returned.
- Existing store, migrate and daemon SIGTERM tests unchanged and green.

## Out-of-scope touches

None.

## Report

- `src/lib.rs`: `Store::close` closes the pool, then, while `ship.db-wal`
  or `ship.db-shm` exists, opens a barrier connection, reads, closes it and
  polls every 10 ms. The wait is bounded by `BUSY_TIMEOUT` (5 s). Signature
  unchanged.
- `src/migrate.rs`: `probe_version` → `probe_version_with(path, copy)`. A
  `NotFound` from the copy step re-checks the WAL, at most 3 attempts. Any
  other error propagates. `sidecar` is now `pub(crate)`.
- `Cargo.toml`: direct `tokio` dependency (`time` only). It was already in
  the lock graph, and `Cargo.lock` is unchanged.
- Tests added: `close_then_reopen_never_fails` (200 rounds, asserts no
  sidecars after each close), `probe_tolerates_wal_vanishing_mid_copy`,
  `probe_propagates_other_copy_errors`.
- `metis verify --post --slice fix-0001`: green on 20 consecutive runs (1 +
  19 with `--force`).
- Not confirmed directly: whether sqlx 0.8.6's `Pool::close` returns before
  the last `sqlite3_close`. This session could not read the sqlx sources or
  run cargo outside `metis verify`, and the pre-fix code was not looped
  here. The fix covers both sides regardless: close waits on the sidecars,
  and open tolerates them going.
