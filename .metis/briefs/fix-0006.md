# fix-0006 — The documented non-root install leaves a daemon systemd cannot start: service install accepts a binary under a home directory

- **Type:** fix | **Risk:** high | **Priority:** p0
- **Coder:** claude-code/opus-5-5 | **Date:** 2026-11-27
- **Plan:** .metis/plans/phase-0-plan.md §0.8

## Goal

§0.8's "on a clean VM, `ship service install` then `systemctl start ship`
yields a running daemon" holds for the path install.sh recommends: install
refuses, before any change, a binary the `ship` user cannot run, and
install.sh no longer recommends `service install` from a per-user prefix.

## Architectural context

- Evidence: `.metis/briefs/phase-0-gate.md`, run 1 (v0.0.1, scenario 1
  FAIL on gate hosts A and B; unit `ExecStart=/home/USER/.local/bin/ship …`,
  home 0750, `status=203/EXEC` loop).
- `crates/ship/src/service.rs` `install()` preflight: foreign unit,
  `check_exe_path`, docker group. `exe_reachability_warning` (o+x on every
  ancestor) only warns, after all changes. `main.rs` passes the canonical
  `current_exe()`.
- Change: the warning becomes a preflight refusal `ServiceError::Refused`
  when (a) the binary or any directory above it is not executable by
  others, or (b) the binary is under a home directory: a root in
  `Layout::home_roots` (system: `/home`, `/root`) or the home of `SUDO_USER`
  (from `getent passwd`, canonicalised). Message names the path and reason
  and gives the exact commands
  `sudo install -m 0755 <exe> /usr/local/bin/ship` and
  `sudo /usr/local/bin/ship service install`, then "Nothing was changed.".
- Testability: `Host` gains `mode(path) -> Option<u32>` (default: real
  `fs::metadata`) and `sudo_user() -> Option<String>` (default: env
  `SUDO_USER`); `Layout` gains `home_roots`. The fake host reports 0755
  except for listed paths, so tests do not depend on the temp dir's real
  modes (macOS temp dirs are 0700).
- `InstallReport::warnings` had this warning as its only source; it is
  removed with it.
- `scripts/install.sh`: after installing on Linux, when the physical prefix
  is under `$HOME`, `/home`, `/root`, or any directory up to `/` lacks o+x,
  print that the daemon needs a system path, the two `sudo` commands, and
  that ssh targets need `ship` on the PATH of a non-interactive ssh session
  (`/usr/local/bin` is). Otherwise the existing hint stays. Default prefix
  choice unchanged.

## Definition of Done

1. `ship service install` with a binary under a home root, under the
   `SUDO_USER`'s home, or below a directory without o+x exits 1 with the
   refusal and the two commands, and issues no mutating command and
   creates no directory or unit.
2. A binary at a system path (all ancestors o+x, not under a home) installs
   exactly as before (existing tests unchanged in behaviour).
3. install.sh on Linux with a per-user prefix prints the system-path
   message and the `sudo install -m 0755 PREFIX/ship /usr/local/bin/ship`
   line, and never `sudo PREFIX/ship service install`.
4. The CI `service` job (`scripts/service-smoke.sh`, no ci.yml change)
   follows the non-root path end to end: install.sh as the runner user into
   a per-user prefix in a 0750 directory under `$HOME`, `sudo` that binary
   `service install` → exit 1, refusal text with the install command, no
   ship user, group, unit, `/var/lib/ship` or `/run/ship` created that did
   not exist before; then the printed `sudo install` command, and the
   existing smoke continues from that copy (service starts, socket 0660, …).
5. docs/service.md and README.md say the daemon needs a system path and
   that a per-user install is refused.
6. `metis verify --post` green; shellcheck clean on the changed scripts.

## Test plan

  (fake mode 0750 on a parent), `binary_under_a_home_root_is_refused_before_any_change`
  (layout home root), `binary_under_the_sudo_users_home_is_refused`

  `sudo install -m 0755 <exe> /usr/local/bin/ship`.
- install-selftest.sh (Linux): the good-release case asserts stdout has the
  system-path line and lacks `sudo PREFIX/ship service install` (prefix is

- service-smoke.sh: DoD 4, run by the CI `service` job on a real runner
  with systemd; not runnable on the laptop (needs systemd and passwordless

  preflight `check_exe_reachable` (after `check_exe_path`, before the docker
  group check): refuses a binary below `Layout::home_roots` (`/home`,
  `/root`) or the `SUDO_USER`'s home (`getent passwd`, canonicalised), or
  with any ancestor lacking o+x. Message names path and reason, prints
  `sudo install -m 0755 <exe> /usr/local/bin/ship` and
  `sudo /usr/local/bin/ship service install`, ends "Nothing was changed.".

  added; `InstallReport::warnings` removed (its only source). 4 new tests.
- `scripts/install.sh`: on Linux, `system_path` (not under `/home`, `/root`,
  `$HOME`; every directory to `/` has o+x via `find -prune -perm -0001`) on
  the physical prefix decides the hint; per-user prints the system-path
  message and the two sudo commands. System path keeps the old hint.
- `scripts/install-selftest.sh`: Linux-only check on the good-release case.
- `scripts/service-smoke.sh`: new opening steps (DoD 4); the existing
  `sudo install` step now follows the refusal. No ci.yml change.
- `docs/service.md`, `README.md`: system path required, refusal described.
