# feat-0001 — ship host: host and Docker status from the CLI

- **Type:** feat | **Risk:** medium | **Priority:** p1
- **Coder:** claude-code/opus-5-5 | **Date:** 2026-11-25
- **Plan:** .metis/plans/phase-0-plan.md §0.6

## Goal

`ship host [-o text|json] [--timeout SECS]` reports the current target's
host and Docker status (a GET of `/api/v1/host`), so the Phase 0 gate's
"stopping Docker changes it to `unreachable` and `ship host` reports the
same" can be checked from the CLI; and README states the idle-daemon
figures measured at the gate.

## Architectural context

- OVERVIEW §6: `ship host  # host and Docker status, as /api/v1/host` in
  the CLI, and `ship host -o json` in the JSON contract (ADR-0004; shapes
  provisional until Phase 5). Slice notes (human decision 2026-11-25) fix
  the output, exit code and README content.
- Consumes, unchanged: `ship_core::{HostInfo, DockerInfo, DockerStatus,
  HostCapacity, HOST_PATH}` (`crates/ship-core/src/api.rs`), the daemon's
  `/api/v1/host` handler (`crates/ship-daemon/src/host.rs`, preflight in
  `crates/ship-docker/src/preflight.rs`), and the existing client path
  `crate::client::get_json` with its API version check, `commands::endpoint`
  and `commands::runtime` (`crates/ship/src/`). No daemon or wire change.
- New dev-dependency: `ship-docker` in `crates/ship` (already a workspace
  crate; `ship` is top-level, so the dependency rule allows it), only so the
  tests can give the in-process daemon a fake or unreachable `docker`
  instead of the developer's real one.

Design decisions:
- **CLI:** `Command::Host(commands::HostArgs)` with `-o/--output text|json`
  (default text) and `--timeout SECS` (1–3600, default 30), as `projects`.
  Help states: exit 0 whenever the daemon answered, whatever Docker's
  status (a report, not a check); 1 when the daemon could not be reached or
  refused; 2 usage error.
- **`-o json`:** `serde_json::to_string_pretty(&HostInfo)` + newline: exactly
  the daemon's body shape, identical bytes over every transport.
- **Text:** one block, Docker's status first; when not `ready`, the
  daemon's message verbatim on the next line:
  ```
  Docker:   unreachable
  Message:  <docker.message verbatim>
  Engine:   unknown (supported >= 24.0.0, < 30.0.0)
  Compose:  unknown (supported >= 2.20.0, < 6.0.0)
  Host:     linux x86_64, 4 CPUs, 15.6 GiB memory, 120.3 GiB disk free
  Daemon:   ship 0.0.1, API v1
  ```
  A capacity figure the daemon could not read prints `unknown`. Sizes in
  GiB with one decimal (binary units, stated by the unit).
- **Fixture:** `crates/ship/tests/fixtures/host.json`, a pretty `HostInfo`
  with Docker `ready`, engine `28.3.2`, compose `2.39.1`, this build's
  supported ranges, and placeholder `version`, `os`, `arch` and `capacity`.
  The CLI test normalises `version`, `os`, `arch` and the three `capacity`
  numbers (each checked to be a number or null first) to the fixture's
  values and then requires the whole JSON value equal to the fixture; a unit
  test requires the renderer to reproduce the fixture byte for byte.

## Definition of Done

- [ ] `ship host -o json` over a `local` target against an in-process daemon with a fake `docker` (28.3.2 / 2.39.1) exits 0 and, after normalising version, os, arch and capacity, equals `crates/ship/tests/fixtures/host.json`.
- [ ] Over an `ssh://` target (the fake `ssh`) it prints the same bytes as over `local`, except the live `disk_free_bytes` value, and also equals the fixture after normalisation.
- [ ] With Docker unreachable, `ship host` exits 0, its first line is `Docker:   unreachable` and the next carries the daemon's message verbatim; `-o json` shows `"status": "unreachable"`.
- [ ] With Docker ready, text output starts with `Docker:   ready`, shows both versions and no `Message:` line.
- [ ] With no daemon, `ship host` exits 1 and names how to start one (same path as `projects`).
- [ ] `ship host --help` says exit code 0 means the daemon answered, whatever Docker's status.
- [ ] README lists `ship host` and states the gate's idle-daemon figures as one measurement, not a guarantee.
- [ ] `metis verify --post` green.
