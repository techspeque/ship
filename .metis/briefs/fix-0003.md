# fix-0003 — CI: SQLite advisory RUSTSEC-2026-0459 fails the audit; shellcheck SC2115 in install-selftest.sh

- **Type:** fix | **Risk:** medium | **Priority:** p1
- **Coder:** claude-code/opus-5-5 | **Date:** 2026-11-25
- **Plan:** .metis/plans/phase-0-plan.md §0.9

## Goal

Make the first CI run of `dev` green on the §0.9 jobs: the dependency audit
passes with no known SQLite vulnerability in the graph, shellcheck passes on
`scripts/install-selftest.sh`, and both install.sh self-test runners always
report a result.

## Architectural context

- `ship-store` is the only crate depending on SQLx (`sqlx` 0.8.6 →
  `sqlx-sqlite` 0.8.6 → `libsqlite3-sys` 0.30.1, bundled SQLite < 3.54.0,
  RUSTSEC-2026-0459 / CVE-2026-119375).
- `deny.toml` `[advisories]` denies every vulnerability; `ignore = []`.
- CI job `install-script` in `.github/workflows/ci.yml` runs shellcheck (Linux)
  and `scripts/install-selftest.sh` on an ubuntu/macos matrix with the default
  `fail-fast: true`.
- sqlx 0.9 requires SQL arguments to be `SqlSafeStr`: `&'static str` passes,
  runtime-built strings need `AssertSqlSafe`. `ship-store` builds a few
  statements at runtime (`repo.rs`, `migrate.rs`).

## Definition of Done

1. `sqlx` upgraded to 0.9.x in `crates/ship-store/Cargo.toml`; `Cargo.lock`
   resolves `libsqlite3-sys` to a version bundling SQLite ≥ 3.54.0, so the
   advisory no longer matches. Preferred path.
2. Only if no fixed `libsqlite3-sys` is reachable: a `deny.toml` `ignore`
   entry with the advisory id and a reason stating the real exposure
   (requires a database or -wal file written by a less trusted party; Ship's
   database lives in the daemon-owned state directory), reported as a
   decision for a person to accept.
3. `ship-store` code adapted to any sqlx 0.9 API change with unchanged
   behaviour; its tests and migrations stay green.
4. `scripts/install-selftest.sh:131` uses `${work:?}` / `${1:?}` so
   shellcheck SC2115 no longer fires.
5. `install-script` job matrix sets `fail-fast: false`, so the macOS and
   ubuntu self-tests both run to completion.
6. `metis verify --post` green.

- Blocked, item 1: `sqlx = "0.9"` resolved sqlx 0.9.1, and `make verify` then failed

  owned_paths. The same resolution kept `libsqlite3-sys` at 0.30.1
  (the vulnerable version), so the bump alone does not clear the advisory.
  Whether sqlx-sqlite 0.9.x accepts a fixed libsqlite3-sys could not be
  checked, because there was no network or cargo registry access. The bump
  was reverted. Parked with `metis wait --human` for a decision on the toolchain
  bump (and the upgrade versus a `deny.toml` ignore).
